# Subagent Dispatch Gate (shared, normative)

Applies to any skill that **prescribes spawning subagents for substantive work** via
the `task` tool. Prevents the **subagent task trap**: an orchestrator reading the
skill and silently doing the subagent's work inline instead of dispatching it.

## Why this exists

A skill that only *describes* "spawn a subagent for X" provides no enforcement.
The orchestrator can read it, understand the intent, and still do X itself —
producing a plausible but non-compliant result. `status` fields are
self-reported and forgeable. This gate makes real dispatch **mechanically
checkable** using evidence the harness itself produces.

## The three mechanisms

### 1. `task_id` ledger (the keystone)

Every time the orchestrator spawns a subagent via the `task` tool, it MUST
record the harness-returned `task_id` in the session state file (or a dedicated
`subagent-ledger-{sessionId}.json`), alongside the subagent's role and its
designated `result_file`.

```json
{
  "role": "qa-agent",
  "task_id": "ses_<harness-returned-id>",
  "result_file": ".agents/results/result-qa-<taskSlug>-<sessionId>.md",
  "status": "complete"
}
```

`task_id` is generated by the harness at spawn time — the orchestrator cannot
fabricate it. A missing or empty `task_id` for a required subagent is proof the
subagent was never actually dispatched.

### 2. Dispatch gate (hard invariant)

Before the orchestrator may **consume** a subagent's deliverable (synthesize,
aggregate, act on, or publish it), it MUST pass the dispatch gate for that
subagent:

- [ ] The subagent has a non-empty `task_id` recorded in the state file.
- [ ] The subagent's `status` is `complete` (not `pending`/`running`/`failed`).
- [ ] The subagent's `result_file` exists on disk and is non-empty.
- [ ] The `result_file` contains the required section marker for that role
      (e.g. `# Section 1` for qa-agent, `# Section 3` for deep-reviewer).

Mechanical check (run from the repo root; substitute your state file path):

```bash
python3 - <<'PY'
import json, os, sys
state = json.load(open(sys.argv[1]))
required = ["qa_alignment", "deep_review", "security_audit"]  # your roles
missing = []
for role in required:
    s = state["subagents"].get(role, {})
    rf = s.get("result_file")
    if not s.get("task_id") or s.get("status") != "complete" \
       or not rf or not os.path.isfile(rf) or os.path.getsize(rf) == 0:
        missing.append(role)
if missing:
    print("DISPATCH GATE FAILED — not dispatched:", ", ".join(missing))
    sys.exit(1)
print("DISPATCH GATE PASSED")
PY
```

If the gate fails, the orchestrator MUST dispatch the missing subagent(s). It
MUST NOT proceed by doing the work inline.

### 3. No inline substitution rule

A subagent's deliverable is **defined** as a file written by a spawned
subagent whose `task_id` is recorded in the state file. Analysis, synthesis,
or output produced directly by the orchestrator does **not** count as a
subagent's deliverable, regardless of quality. Inline work may supplement but
never replace a required subagent's deliverable.

## Where to add the hooks

Each consuming skill MUST add, at minimum:

1. A `task_id` field to every subagent entry in its state file schema.
2. A **Dispatch Gate** step at the boundary *before* the step that consumes the
   subagent outputs (synthesis / aggregation / publish), referencing this file.
3. A **no inline substitution** rule in its Guardrails / rules section,
   referencing this file.
